# 0.1.3：同一弹窗确认与刷新后的历史链接核对

目标发布版本：`0.1.3`。本文说明当前修复及安全边界；文档更新不代表已有 0.1.2 构建已升级。最终版本与测试结果须核对实际发布包及 `TESTING.md` 最终报告。

## 两个独立问题

### 正常流程不应依赖重开后的密码回显

用户提交的 0.1.2 构建已通过 `manualReview` 解决“人工采用后又重开验证”的循环，但正常自动流程仍会关闭、重开分享弹窗验证密码。

本次对公开官方 JS 的只读核对证实，分享弹窗组件新建时 `pwd` 为空。**组件新建后的空值不代表服务端密码丢失**，也不能反向证明历史密码有效。把空白显示当成未设密码，可能触发不必要的补码，旧版补码也可能已经替换历史密码。因此不能继续承诺“始终保留已有密码”。

0.1.3 正常流程只在同一弹窗内确认项目、URL 和有效密码状态，记录 `verification: same_dialog`，不再为了验证关闭后重开。当前弹窗可读取有效密码时不主动改写；已有密码记录但当前弹窗不回显时暂停核对，不自动覆盖。

### 刷新后没有弹窗，原人工入口无法采用

0.1.2 的人工入口必须通过 `READ_REVIEW` 读取当前受保护弹窗。刷新微云 tab 会使该弹窗消失，即使本项 URL 和历史密码仍在本地，原入口也会失败：

```text
分享弹窗已消失，需要核对。
DIALOG_MISSING
```

本轮在 isolated Edge fixture 稳定复现了完全相同的错误，并在修复后的历史链接恢复路径转绿。该证据仅说明刷新恢复回归已覆盖，不是对真实微云账号执行分享的证明。

## 变更范围

既有 0.1.2 `manualReview` 改动同步回 TypeScript 源，并保留原有安全校验、恢复顺序及历史链接信息。0.1.3 不取消 `needs_review`，也不把本地旧密码自动认作服务端有效密码。

面板新增同组 radio：

- **读取当前分享弹窗**：读取准确项目的当前受保护弹窗；用户确认后采用，不为该人工项再次打开分享或添加密码。
- **页面已刷新 / 弹窗已关闭：核对历史链接**：从本项已记录 URL 中选择，用户在分享访问页核对有效密码并手动填写，明确勾选后保存人工结果。

只有主动选择历史方式时，`READ_REVIEW` 的 `DIALOG_MISSING` 才允许进入历史核对。当前弹窗方式仍要求弹窗存在；其他读取错误或弹窗冲突不因切换来源而被忽略。

## 历史方式的输入约束

| 输入 | 约束 |
| --- | --- |
| URL select | 仅允许本项 `observedUrl`、`candidate.url`、`relatedShares`、`error.relatedUrls` 中合法并去重的 URL；后台再次检查归属，不接受任意新链接或其他项目链接 |
| 密码 | 用户本次手动输入已在分享访问页确认有效的密码；不能为空，须为 4–16 位字母或数字，不自动回填 `observedPassword` 或候选密码 |
| 历史密码 | 仅可展开查看，明确标注“可能已过期，仅供核对”，不代表当前有效，不构成人工批准 |
| 勾选确认 | 必须明确包含原账号、访问页确实需要该密码且内容对应本项、已经处理相关链接 |

历史方式的确认说明为：

> 我已确认原账号，在分享访问页验证了所选链接需要此密码且内容对应本项，并已处理相关链接。

仅打开链接或在已登录状态下直接看见内容，不足以证明分享访问需要所填密码。用户必须核对真实的密码要求及对应内容；无法确认时应保持暂停，不能为了继续而勾选。

## 持久化与执行顺序

1. 校验原目录、账号、当前 `documentNonce`、任务 `revision` 及 `itemKey`（`TaskItem.key`，提交字段 `reviewKey`），并要求明确勾选。稳定账号标识不可读时需手动确认原账号。
2. 检查 URL 合法且属于本项历史记录，不与其他已完成项的结果重复；检查密码非空且格式有效。若当前仍有弹窗，错误项目、不同 URL 或可见密码冲突必须停止。提交前再次核对页面 context，保存时再次核对 revision。
3. 先持久化 `manualReview`，包含所选 URL、本次手动密码、人工确认时间及 `source: saved_link`，将该项置为 `verifying`。其他观察、候选及错误中的合法历史链接合并保留，不因采用一个 URL 就丢失。
4. runner 优先处理该批准项，使用持久化批准生成 `verification: manual_review`、`reviewSource: saved_link` 的结果；**对该项不调用 `openShare` / `addPassword`**，不重新分享、不补码，也不要求消失的弹窗重新出现。
5. 提交 `item_done`，完成持久化收到 ACK 后才执行关闭及后续项目。没有弹窗时 `closeShare` 为 noop；关闭失败保留已完成结果并暂停，storage 失败或缺少 ACK 时不继续后续变更。

当前弹窗人工采用记录为 `manual_review` / `current_dialog`，保存时仍检查当前弹窗与批准的链接、密码一致。自动流程则记录 `same_dialog`。这些标签不能互相冒充，也不能表示插件独立访问接收端或验证了服务端状态。

历史方式不推测不可读取的有效期；确认时间是用户批准时间。继续原任务只避免为**当前已人工采用项**重复分享，剩余未完成项目仍可能创建链接或添加密码。

## 仍然有效的安全与历史规则

补充回归保护：面板忙碌期间收到页面刷新通知会排队重新连接，而不是丢弃通知后持续提交旧 `documentNonce`；保存历史批准项时只关闭属于该项的弹窗，不会关闭另一待核对项的当前弹窗。URL 去重统一解析 origin、默认端口和末尾斜杠，避免同一链接以大小写主机名等不同写法被重复采用。这些场景均先以本地测试复现失败，再验证修复。

- 目录或账号变化、document 刷新、任务 revision / itemKey 过期、旧 runner 写入均应阻止继续，重新读取后才可核对。
- 非法 URL、与其他已完成项重复的链接、空或无效密码、当前弹窗冲突不能通过人工入口绕过。
- 已知进行中的项目及人工批准优先于未触碰项目；不确定外部变更不能自动当作安全失败重试。
- 意外链接及其他历史链接继续保留，必要时先记录再尝试保护并暂停。列出链接不代表已取消；插件不自动撤销微云分享。
- 创建分享与启用密码仍是分开的 UI 动作，无法保证新链接创建瞬间已有密码。

## 导出与外部备份

TXT 中人工项必须注明“人工确认，非独立服务端/接收端验证”，并区分当前弹窗与历史链接来源；`same_dialog` 仅表示同一弹窗显示确认。旧的 `reopened_dialog` 结果保留历史含义，不追溯升级证据强度。

已完成项的其他历史相关链接仍列入 TXT 和进度，注明不代表已取消。JSON 备份含链接和密码，必须妥善保管；它不是加密保险箱。

**外部导入的 `manual_review` 备份不自动当完成，也不继承原人工批准。** 导入后作为候选，要求在当前目录、账号、页面和项目上再次人工确认。不要把原本机 storage 的续跑与外部文件导入混为一谈。

## 用户升级与恢复步骤

1. **先导出进度 JSON 备份**，按需导出部分 TXT；运行中的任务先暂停，等待当前项保存完成。
2. 将 0.1.3 发布内容覆盖原来加载的**同一个目录**，不要卸载、清空 storage、更换 browser profile 或加载目录，以保留 extension ID 和本地进度。
3. 在 `chrome://extensions` 或 `edge://extensions` 重新加载，确认显示 `0.1.3`；仅复制文件不等于升级完成，仍为 0.1.2 时不要继续。
4. 刷新微云 tab，回到原账号及原目录，点击工具栏插件图标读取**原任务**；账号无法自动识别时按提示明确确认。
5. 弹窗已消失时选择“页面已刷新 / 弹窗已关闭：核对历史链接”，从该项 select 选择原记录 URL，在另一个 tab 打开访问页，核对密码要求、有效密码及内容归属。
6. 手动输入本次有效密码，检查并处理相关链接，勾选完整确认说明，点击“保存人工核对结果并继续”。只继续原任务，**不要重新建立任务**。

如果确实不知道有效密码，且展开查看的历史密码也无效，插件不能从服务端恢复密码或从空白弹窗推算。应保持暂停、保留备份及相关链接，不应盲目重新分享或反复添加密码。

## 验证与未完成项

刷新后的同一 `DIALOG_MISSING` 错误已用 isolated Edge fixture 稳定复现并转绿。正常同一弹窗确认、两种人工来源、来源及输入约束、账号/页面/任务过期、冲突与重复 URL、存储 ACK 顺序、关闭失败、历史导出及外部人工备份再确认等最终测试结果，以发布包 `TESTING.md` 最终报告为准；本文不写死测试数量，也不把历史报告当作本轮重新运行的结果。

本轮真实云盘没有写入、创建新分享或修改密码。既有真实列表 1–60 项及 lazy loading 的只读核对，不等于真实 60 项分享端到端验收。真实服务端密码保存、接收端访问、链接复用、限流、DOM 差异及手动安装链路仍需独立验证，不承诺固定完成时间。
